# AGENTS.md

Instructions for any AI coding agent working in this repository. Read this file fully before doing anything, and re-read the relevant section whenever you are unsure.

---

## 1. Project goal

Build a **simple, gamified MCQ practice website** using only **HTML, CSS and vanilla JavaScript**.

The source material is a set of PDFs in `assets/`, one per week, from **Week 1 to Week 11**. Each PDF contains multiple-choice questions together with their answers. Some questions include figures, charts, graphs or tables, and some options may be images.

The website lets the user:

1. Pick a week (1–11), or a mixed mode across all weeks.
2. Click an answer and instantly see whether it is **right or wrong**.
3. Earn points, streaks and badges while practising.

**Hard rule: the site never shows explanations, reasoning, hints or solution text.** It only tells the user right or wrong.

---

## 2. Tech constraints

- Plain **HTML + CSS + JavaScript (ES6+)**. No frameworks, no bundlers, no npm runtime dependencies for the website itself.
- The website must work by **double-clicking `index.html`** (opened via `file://`) as well as from a static host. Therefore do **not** rely on `fetch()` for local JSON. See section 4 for how data is bundled.
- Extraction tooling may use Python (PyMuPDF, optionally pdfplumber and pytesseract). Tooling lives in `scripts/` and is never loaded by the website.
- Progress is stored in `localStorage`. No backend, no accounts, no network calls except the Google Fonts stylesheet.

## 4. Data model

One JSON file per week, `data/weekNN.json` (zero-padded), containing:

```json
{
  "week": 3,
  "source_pdf": "assets/week3.pdf",
  "questions": [
    {
      "id": "w03-q012",
      "number": 12,
      "type": "single",
      "question": {
        "text": "Which of the following is shown in the graph?",
        "images": ["assets/figures/week03/q012-fig1.png"]
      },
      "options": [
        { "id": "A", "text": "Option text", "image": null },
        { "id": "B", "text": "", "image": "assets/figures/week03/q012-optB.png" }
      ],
      "answer": ["B"],
      "source": { "page": 4 }
    }
  ]
}
```

Field rules:

- `type` is `"single"` (one correct option) or `"multi"` (more than one correct option, e.g. "select all that apply"). Derive it from the PDF, not from guesswork.
- `answer` is always an array of option ids, even for single-answer questions.
- `question.images` is an array (possibly empty). `options[].image` is a path or `null`.
- Preserve the original question numbering in `number` and the original option labels in `id`.
- **Do not add an `explanation`, `hint`, `rationale` or similar field.** Even if the PDF has one, discard it.

`scripts/build_data.py` merges all week files into `data/quiz-data.js`:

```js
window.QUIZ_DATA = { "1": [ ... ], "2": [ ... ], ... "11": [ ... ] };
```

`index.html` loads it with a normal `<script src="data/quiz-data.js"></script>` tag so the site works from `file://`.

## 5. Extraction workflow (PDF to data)

Work week by week. Do not skip weeks and do not batch-guess.

### 5.1 Discover inputs
List `assets/`. Match each PDF to a week number using its filename. If a week is missing or a name is ambiguous, stop and ask the user.

### 5.2 Inspect each PDF before extracting
Before writing any extraction code for a week, look at it: extract the text of the first few pages and rasterise one or two pages to view the layout. Work out:

- How questions are numbered.
- How options are labelled (A–D, a–d, 1–4, i–iv).
- **Where the answers live**: an answer key at the end, a marked line under each question, bold or ticked options, or something else. Different weeks may use different formats. Handle each week on its own terms.
- Whether pages are text-based or scanned. If scanned, use OCR and flag lower confidence in the report.

### 5.3 Extract text
Use PyMuPDF (`fitz`) for text blocks with coordinates. Keep original wording exactly. Only fix obvious extraction artefacts (broken ligatures, hyphenation at line ends, stray page numbers or headers/footers). Preserve maths symbols, units, subscripts and code snippets.

### 5.4 Extract figures, charts, graphs and tables
These **must come straight from the PDFs**. Never redraw, recreate, approximate or replace them with generated images.

- Use the coordinates of the question block to find any embedded image or vector drawing belonging to it.
- Embedded raster images: extract the original image.
- Vector charts, graphs, tables and diagrams (these are not embedded images): **render the page region to PNG at 200–300 DPI** using a clip rectangle around the figure, with a small margin.
- Crop tightly so the figure does not include neighbouring questions or options text, unless the figure and the options are inseparable.
- If an option itself is an image, save it as `qNNN-optX.png`.
- If a table is part of the question, prefer the cropped image over reconstructing it as HTML, so it matches the PDF exactly.
- Save to `assets/figures/weekNN/` with predictable names: `qNNN-fig1.png`, `qNNN-optB.png`.
- Optimise file size reasonably (PNG, or WebP if clearly smaller) without visible quality loss.

### 5.5 Extract answers
Record the correct answer(s) exactly as the PDF states them. **Never solve a question yourself to fill a gap**, and never override the PDF's answer with your own opinion. If an answer is missing or contradictory, leave it out, add the question to `reports/extraction-notes.md` under "Needs review", and tell the user.

### 5.6 Validate
`scripts/validate.py` must check, for every week:

- Question numbers are sequential with no gaps or duplicates (or the gaps are explained in the notes).
- Every question has at least 2 options, and every option has text or an image.
- Every question has a non-empty `answer` whose ids all exist in `options`.
- Every referenced image file exists.
- Total count per week matches what the PDF shows. State the count in the notes.
- No JSON field contains an explanation or hint.

After validation, visually spot-check at least 3 questions per week (including every question that has a figure) by opening the cropped image next to the PDF page.

### 5.7 Report
Write `reports/extraction-notes.md` with, per week: question count, answer-key format found, number of figures extracted, anything uncertain. Surface all uncertainties to the user in your final message. Do not bury them.

## 6. Website behaviour

### 6.1 Screens
1. **Home**: title, week grid (Week 1 to Week 11) showing progress per week, a "Mixed practice" option, current streak, total XP, theme toggle.
2. **Quiz**: one question at a time, progress indicator, live score and streak.
3. **Results**: score, accuracy, XP earned, badges unlocked, buttons to retry, review missed questions, or go home.

### 6.2 Answering rules
- **Single-answer questions**: clicking an option checks it immediately.
- **Multi-answer questions**: options toggle; a "Check" button submits the selection. The result is right only if the selected set equals the answer set exactly.
- Feedback is **only** right or wrong. No explanation text, no hints, no "because".
- On a **right** answer: mark the option, play a small success animation, lock the question, enable "Next".
- On a **wrong** answer: mark the clicked option as wrong with a short shake, keep the other options available so the user can try again. Do **not** reveal the correct option. Only the **first attempt** counts for score and accuracy; later retries do not earn XP.
- Option order stays as in the PDF (do not shuffle option order, as labels like "A and B only" depend on it). Question order may be shuffled via a toggle.
- Images in questions and options can be tapped to open a larger view (simple lightbox, close on tap, Esc or backdrop).

### 6.3 Gamification
Keep it light, motivating and tasteful. Suggested mechanics:

- **XP**: base points per first-attempt correct answer, plus a streak multiplier (e.g. x1, x1.5, x2 as the in-a-row count grows).
- **Streak**: consecutive first-attempt correct answers within a session. Also a **daily streak** (days practised in a row).
- **Levels**: derived from total XP, shown on Home with a progress bar toward the next level.
- **Week mastery**: each week shows 0–3 stars based on best accuracy (for example 60%, 80%, 95%).
- **Badges** (small set, simple icons): first correct answer, 5/10/20 streak, week completed, week mastered, all 11 weeks completed, 7-day practice streak.
- **Challenge mode (optional toggle)**: 3 lives, a life is lost on a wrong first attempt, session ends at 0 lives.
- **Review mode**: replay only the questions previously answered wrong.

All state lives in `localStorage` under a single namespaced key (e.g. `mcqPractice.v1`). Provide a "Reset progress" action with a confirmation dialog. Wrap every storage read and write in `try/catch` and fall back gracefully if storage is unavailable.

## 7. Design system (strict)

### 7.1 Typography
- Font: **Rajdhani**, loaded from Google Fonts with only the weights used:

```html
<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
<link href="https://fonts.googleapis.com/css2?family=Rajdhani:wght@300;400&display=swap" rel="stylesheet">
```

- **Questions: Rajdhani Regular, weight 400.**
- **Answer options: Rajdhani Light, weight 300.**
- All other UI text (buttons, labels, headings) uses Rajdhani 400. Do not use any other weight or any other font family. The fallback stack is `"Rajdhani", system-ui, sans-serif`.
- Because light text is thin, make sure option text is at least 1.1rem and has strong contrast against its background.

### 7.2 Colour
- **One theme palette only**: one accent colour plus neutrals. No extra hues.
- **No gradients anywhere** (backgrounds, buttons, borders, text, shadows). Flat solid colours only.
- Define everything as CSS custom properties on `:root`, with an override for dark mode. Starting palette (adjust the accent only if the user asks):

```css
:root {
  --bg: #F5F5F0;
  --surface: #FFFFFF;
  --text: #14181B;
  --muted: #5B646B;
  --border: #D9DDD8;
  --accent: #0F766E;
  --on-accent: #FFFFFF;
}
:root[data-theme="dark"] {
  --bg: #0E1213;
  --surface: #161C1E;
  --text: #E8ECEA;
  --muted: #8E9A97;
  --border: #263033;
  --accent: #2DD4BF;
  --on-accent: #0E1213;
}
```

- **Right / wrong feedback without extra colours**: do not introduce red and green. Use the accent for the correct state (solid accent fill, `--on-accent` text, a check icon) and use neutrals plus shape for the wrong state (strikethrough-style dashed border, muted text, an ✕ icon, and a shake animation). Feedback must never rely on colour alone. If the user later asks for red/green, change it in one place via variables.
- Contrast: body text and option text must meet WCAG AA in both themes.

### 7.3 Dark and light mode
- Both modes are required and fully styled.
- Default to the OS setting via `prefers-color-scheme`. A visible toggle lets the user override, and the choice is saved in `localStorage`.
- Apply the theme by setting `data-theme` on `<html>` **before first paint** (small inline script in `<head>`) to avoid a flash of the wrong theme.
- Add `color-scheme: light dark` so form controls and scrollbars follow the theme.

### 7.4 Responsive behaviour
The site must work on every screen size, from 320px phones to large desktop monitors.

- Mobile-first CSS, fluid layout with `clamp()` for type and spacing, CSS Grid/Flexbox, relative units.
- Content column max width around 800px on large screens; week grid reflows from 2 columns on small phones up to 4 or more on desktop.
- Tap targets at least 44x44px. Options are full-width buttons on small screens.
- Images: `max-width: 100%; height: auto`. Wide figures, tables and charts scroll inside their own container or open in the lightbox. **The page body must never scroll horizontally.**
- Use `100dvh` (with a `vh` fallback) for full-height layouts. Respect safe-area insets on notched phones.
- Include `<meta name="viewport" content="width=device-width, initial-scale=1">`.
- Test at 320, 375, 768, 1024, 1440 and 1920px wide, in portrait and landscape.

### 7.5 Motion and accessibility
- Animations are short (150–400ms) and flat (opacity, transform). Wrap them in `@media (prefers-reduced-motion: no-preference)`; with reduced motion, replace them with instant state changes.
- Semantic HTML (`main`, `header`, `button`, `fieldset`/`legend` for options). Visible focus rings. `aria-live="polite"` region announcing "Correct" or "Wrong".
- Keyboard support: `A`–`D` or `1`–`4` to select, `Enter` to check/continue, `Esc` to close the lightbox.
- Every figure has meaningful `alt` text (for example "Figure for question 12, week 3").

## 8. Coding conventions

- Small, readable, commented modules. No globals except `window.QUIZ_DATA`.
- Escape or `textContent` all question text when rendering. Do not inject PDF text with `innerHTML` unless it has been sanitised.
- Preload the next question's images to avoid layout jumps. Set `width` and `height` on images where known.
- Keep CSS organised: variables, base, layout, components, themes, utilities. No inline styles in the HTML.
- No console errors or warnings in a clean load.

## 11. Things the agent must never do

- Never invent, rewrite or "improve" questions, options or answers.
- Never answer a question from your own knowledge when the PDF's answer is missing or unclear. Flag it.
- Never add explanations, hints, rationales or solution walkthroughs, in the UI or in the data.
- Never redraw or regenerate figures. Always crop from the PDF.
- Never add gradients, extra colours, extra fonts or extra font weights.
- Never add a framework, build step or backend.
- Never modify or delete files in `assets/` that are original PDFs.
- If something is ambiguous (file naming, answer format, a question you cannot parse), stop and ask the user instead of guessing.
